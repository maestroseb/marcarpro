# Marcar Pro — notes for Claude

Overlay annotation app for a **ViewSonic ViewBoard IFP7533** (Android 13, 3840x2160 @ 480 dpi
= 1280x720 dp). The user is a teacher and writes in Spanish; the panel is only reachable at
school (ADB over Wi-Fi to the panel's address on the school network, needs an on-screen re-authorization after reboots).

## Build
- `JAVA_HOME=~/Library/Java/JavaVirtualMachines/jbr-21.0.11/Contents/Home ./gradlew assembleRelease lintDebug testDebugUnitTest`
  (Android Studio's bundled JBR is Java 25, which Gradle 8.13 cannot run on).
- **The panel runs the release build** (`app-release.apk`, ~180 KB, R8 + shrinkResources, signed with
  the local debug key so it updates over a debug install). Instrumented tests need the debug build.
  `app/src/main/baseline-prof.txt` makes ART compile the whole app at install.
- AGP 8.13.2 / Gradle 8.13 / Kotlin 2.3.21 / compileSdk 36. Don't bump `core-ktx` ≥ 1.19 or
  `activity-ktx` ≥ 1.13: they require AGP 9.1.
- Lint must stay at 0 errors; the only accepted warnings are the version ones above.

## Input model (the important part)
The panel's digitizer (`IRtouch-algo`) reports **every** contact as `TOOL_TYPE_FINGER` with a
constant pressure of 0.5, even though it declares a STYLUS source. Pen, finger and fist are told
apart by `getTouchMajor()` at touch-down (measured on the real panel):

| Contact | touchMajor at DOWN | max during gesture |
|---|---|---|
| Pen fine tip | ~1.4 | ~3 |
| Finger | ~3.2 | ~7.8 |
| Fist / palm | 27–40 | ~40 |
| Pen thick end | 3.2 (same as a finger) | ~5.2 |

Thresholds live in `AnnotationView` (`IR_PEN_MAX = 2.2`, `IR_PALM_MIN = 15`) and only apply to
devices whose name contains `IRtouch`; other devices use the reported tool type. `adb shell
getevent` shows nothing on this panel (devices are grabbed) — calibrate with in-app logging.

## Behaviour
- Pen → ink with the ring's tool. Finger → selection gestures or the app below (see the spec
  below). Fist → partial erase (`Stroke.cut`).
- Strokes join a group (≈ a word) via `WordGrouper` (pause ≤ 1 s, same line, gap ≤ 0.4 × the
  writer's median stroke height; marks attach to their word). Only the last 96 strokes are fed in.
- Pause mode makes the ink window untouchable at 80 % alpha (Android 12+ requirement for
  touches to pass through another app's overlay).
- Committed ink lives in one full-screen bitmap. Every bounded change (erase, select/move, recolour,
  undo, delete, paste) repaints only the affected bounds (`invalidateLayer` → `repaintDirty`, 2 px
  margin); a full repaint only on page switch, clear and resize. Live strokes rebuild their outline once
  per frame (`Live.stale`), not per touch event; `StrokeGeometry` reuses per-thread scratch buffers.
  No redo (nothing in the UI uses it).
- **Rendering on the panel (measured 2026-10-05, `dumpsys gfxinfo … framestats`):** Mali-G52 (Amlogic
  sc2), Skia GL, EGL has `KHR_partial_update` but not `EXT_buffer_age`, so HWUI redraws the whole 4K
  window every frame: ~10–13 ms of GPU just for that (memory bandwidth), with periodic ~30 ms spikes;
  a teacher's session showed a 65 ms median (cause not reproduced with injected strokes: stroke length
  doesn't matter; the old full-screen grid shader on the whiteboard was a suspect). Front-buffered
  rendering (`androidx.graphics` CanvasFrontBufferedRenderer) is NOT possible: `HardwareBuffer.isSupported(
  …USAGE_FRONT_BUFFER…)` = false. Done: committed ink in 512 px tiles (`InkLayer`, only inked tiles drawn
  and re-uploaded, no bitmap where there's no ink); whiteboard paper = clear + `drawPoints` grid; motion
  prediction (`androidx.input:input-motionprediction`, a short predicted segment for the single live pen
  stroke; the ink view is built on a window context because the predictor reads the display).
  Benchmark: inject a long stylus scribble with `adb shell input stylus motionevent …` in one shell and
  read framestats (scripts were in the session scratchpad; undo the stroke with a long press on the orb).
- **Saving:** only boards that changed are written (`changed`), through `AtomicFile` (synced: the panel
  is often switched off at the wall); a board left empty deletes its file. Saved ink is read and decoded
  on the IO thread (`loadBoard` → `AnnotationView.addSaved`, appended after anything written meanwhile),
  so the orb appears at once.

## Testing without the panel
Use the emulator (`emulator-5554`); run `adb shell wm density 240` to mimic 1280x720 dp and
`wm density reset` afterwards. Inject pen input with `adb shell input stylus motionevent
DOWN|MOVE|UP x y` and finger input with `input touchscreen ...`. The emulator cannot reproduce
IR contact sizes, so size classification can only be verified on the real panel.

## Agreed redesign (Oct 2026) — implemented
Interactive mock-up: https://claude.ai/artifact/SzGxrMtTYWoQhiYrXvEjVG (reference look: teal orb
`#3e8784` with halo, white circular satellites with dark labels on a dashed orbit, light card menus).
- **Main orb** (draggable). Tap → full ring of satellites (fan towards the centre when near an edge);
  auto-closes after 10 s idle. **Long-press the orb = undo** (no undo satellite).
- **Launch:** no home screen. `MainActivity` is invisible (translucent theme): it asks for the overlay permission (and notifications once) only when missing, starts `OverlayService` and finishes. The layer starts on the cursor ("using the screen", `paused = true`, the user's choice 2026-10-09) and opening the app never switches to writing: the orb does.
- **Close:** drag the main orb onto the × that appears at the bottom centre (it snaps and turns red when close enough). The board is saved to `files/board.mkp` (`InkStore`, 1.5 s after each change and on exit) and restored on the next launch; undo history starts fresh.
- **Per-tab ink:** `TouchRelayService` (accessibility, `canRetrieveWindowContent`) reads only `<browser>:id/url_bar` of Chromium browsers (`PageKeys.BROWSERS`, Brave on the panel) a moment after window/content changes; each page key (`PageKeys.fromAddressBar`) gets its own `AnnotationView.Board` (ink + undo), any other app shares the general board. Boards stay in memory (LRU 24) and on disk as `page_<sha256>.mkp` (addresses never stored; files unused for 30 days are deleted). A switch waits until the pen lifts. Untested on a real browser yet: the emulator's Chrome is stuck on its first-run screen and the service is off there. Limitation: ink doesn't follow scrolling within a page.
- **PC/HDMI source (OPS):** the overlay works over Windows (verified 2026-10-05: pen writes, finger moves ink, finger/scroll/zoom reach Windows, multi-pupil OK). But the panel also sends every touch to the PC, so a pen stroke scrolled the PDF underneath. `PanelTouch` talks to the vendor open SDK (exported, no permission: bind `com.ifpdos.opensdk.SERVICE_MANAGER` in `com.seewo.mcuservice` → `ISDKServiceManager.getService("opensdk")` (code 1) → `ISDKService.getToken(pkg, "pkg:0")` (code 1) → `sendMessage(token, {"paramsJson","requestName"})` (code 3); reverse-read from the stock Marcar, `com.seewo.easimark`) to declare "no-touch areas" (`CmdAddOrUpdateNoTouchArea` / `CmdRemoveNoTouchArea`, ids 7701–7706, screen px; the panel numbers each area and removal needs that number): the orb, ring, trash and palette, and the whole screen while writing on an external source (see "PC source, final design"). Logs under tag `MarcarPanel` (verbose only in debug builds).
- **Colours (2026-10-05):** 8 presets incl. white (`Presets.COLORS`, same order as `ink_color_names`); the ink colour is stored as ARGB (`Prefs.inkColor`, migrated from the old index via `OLD_COLORS`); up to 6 custom colours (`Prefs.customColors`) made with `ColorPickerView` (SV square + hue bar, ink follows live, "Guardar color" saves). Each ink tool keeps its own colour (`Prefs.colorFor`: the highlighter its own, yellow at first; pen and shapes share the pen's).
- **Colour ring (2026-10-08):** the orb's colour dot (`OrbButton.downOnDot`) opens `ColorRingView` (own window under the orb, like the tool ring; shares `AREA_RING`, never open together): presets + customs + a rainbow "+" (opens the palette card on the picker) on a full ring (≥120 dp), or near an edge a half-moon fan towards the centre on arcs of 120/172/224 dp, 46 dp apart. Tap the dot → tap a colour; or press the dot and slide (`FloatGestures.slideEnabled/onSlide`: the orb doesn't move) and let go on a colour. Thickness is NOT in it (the user's choice): it stays in the card that opens on a second tap of the pen in the tool ring.
- **Ring look:** each `RingItem` has its own `tint`; `SatelliteView` is flat (like the main orb): a pastel of that colour with the icon in its deep shade at rest; the chosen one turns to the full colour, white icon, white rim, halo and a pill in its colour.
- **Shapes (2026-10-05 rewrite):** `ShapeRecognizer` judges closed strokes by their convex hull (hull/min-area-rectangle fill: rect ≈1, ellipse π/4, triangle ½; largest-triangle/hull fill for triangles), then tidies: sides within 10° of level snap, near-square → square, near-round → circle sized by the mean reach. Recognised strokes (`uniform`) skip the streamline smoothing so corners stay sharp; polygons start/end mid-side so the caps don't round a corner.
- **Cursor badge (2026-10-05, same on every source):** drawn inside `OrbButton` (same window, so no overlapping touch regions), on the orb's rim at two o'clock, always (the user's choice; the orb's Floater keeps 50dp from the right edge, `coreRight`, so the badge isn't cut). `downOnBadge` (set in dispatchTouchEvent) tells a badge tap from an orb tap; a long press on it doesn't undo. Tap = writing ↔ "using the screen" (pause: the ink window is NOT_TOUCHABLE, so the finger scrolls Android natively and, on the PC, nothing is reserved). While paused, tapping the main orb also brings the pen back. "Several pupils" (finger writes) is the ring item `RingToggle.PUPILS`. Chosen after live finger routing failed on the panel: the IR digitizer reports the pen as a finger, and a window can't split one gesture between itself and the app below, so a Smart-style pen/finger split needs either a real stylus tool type or system privileges.
- **PC source, final design (2026-10-05):** per-stroke reservation arrives too late (the MCU routes a contact at touch-down; verified with a half-screen experiment: a reservation made beforehand works). So on an external source (`PanelTouch` polls `CmdGetCurrentSource` every 2 s; reply `sdkSourceItem` ANDROID/PC/HDMI…) the whole board stays reserved while writing; the orb's cursor badge toggles "using the PC" (= pause, nothing reserved); "several pupils" is in the ring. `SEND_POINTER` (inject touches into the PC) exists in the SDK but is not implemented in this firmware's UdiServer. Same mechanism for Windows or Linux on the OPS.
- **Live touch routing (TouchInteractionController, API 33) — tried and REMOVED (code deleted in the 2026-10-05 review, never committed):** meant to give fingers real-time scroll in Android by routing each touch at touch-down via touch-exploration mode (`FLAG_REQUEST_TOUCH_EXPLORATION_MODE | FLAG_SEND_MOTION_EVENTS`, `canRequestTouchExplorationMode`) + `requestDelegating()`, making the ink window untouchable for gestures handed to the app. On the IFP7533 it left the panel almost without touch (sidebar and source switching included); no errors logged. Recovery used: `adb shell am force-stop com.maestroseb.marcarpro` (turns touch exploration off, but also disables the accessibility service — the user must re-enable it). Don't try it on the panel again without testing on the emulator first and having ADB connected.
- **Finger drag on empty space (Android source):** replayed on the app after the finger lifts (`onPassThroughDrag` → `TouchRelayService.drag`). The user judged it unusable (late and jumpy); real-time scroll still unsolved. Lasso = hold the finger still 450 ms, then drag.
- **Sidebar (`com.ifpdos.systembar`):** its tool list is fixed in its own assets (`all_tools_app_config.json`, /vendor, read-only); "Marcar" starts `com.seewo.easimark` by package. No supported way to add or replace tools; the app section accepts drag-and-drop from "All apps" (Android source only).
- **Orb position:** first launch against the right edge at 40 % height; afterwards wherever it was last dropped (closing via × keeps the previous spot).
- **Windows:** the orb (fixed 110 dp) and its ring are separate windows; the ring window sits under the orb, is NOT_TOUCHABLE while closed and only moves while empty. Never resize a window holding visible content: the WM moves it a frame before the new buffer arrives and it visibly jumps.
- **Ring edit mode (2026-10-08):** holding a tool in the open ring → tools wiggle, "–"/"+" badges (drawn by `OrbitLayout.dispatchDraw`, above every tool), "Listo" pill between orb and tools; drag reorders live, "–" leaves the tool faded in the ring while editing and out of it afterwards; the pen can't be removed. Tap Listo, around the tools or the orb to finish. Saved as `Prefs.ringOrder` / `ringHidden` (`RingItem.key`); tools added by later versions go at the end.
- **Cut out to the whiteboard (2026-10-08):** scissors badge at two o'clock on the whiteboard button (`MiniOrbView(badgeRes)`, window 84 dp, `coreRight` 44 dp). Flow (`OverlayService.startCrop`): closes the whiteboard if open (the page under it is what gets cut), hides our floating controls (ink stays), `TouchRelayService.screenshot` (`takeScreenshot`, API 30+, `canTakeScreenshot`: needs the accessibility service on, else the prompt below), on an external source (PC/HDMI) it doesn't try: verified 2026-10-09 that Android's capture is black there and the panel refuses `CmdSetShotType VIDEO_AND_OSD` (`result:false`), so a message explains it (Win+Shift+S on Windows); a black capture elsewhere = message, `CropView` (frozen screen 1:1 at its screen position, dim outside the box, corner handles, "A la pizarra"/"Cancelar"), then the whiteboard opens and `AnnotationView.addPicture` puts it under the previous cutouts (or near the top), at its on-screen size (max 90 % width / 50 % height), and scrolls it to the top. A cutout is a `Stroke` with `InkTool.IMAGE` (4 corner points + bitmap + PNG `imageData`, saved inline by `InkStore`; old app versions can't read such a file): selecting with the lasso, moving, scaling, rotating, undo and clear-all work as for ink; the eraser skips it and, on paper, a finger on it pans (no pick-up).
- **Throw and paste on the whiteboard (2026-10-10, emulator-verified, not on the panel yet):** a flicked object now also flies on the whiteboard, bouncing off the part of the board on screen (`flightArea` = `visibleWorld()`, speeds compared × zoom); `settle()` lands a flight before the exit save (it used to save the old place). Long press + lift on an empty spot of the whiteboard → `onPasteRequest` → `OverlayService.pasteFromClipboard`: Android only lets the focused window read the clipboard, so the ink window drops `FLAG_NOT_FOCUSABLE` until `onWindowFocusChanged(true)` (400 ms fallback), reads `primaryClip`, then `applyCanvasWindow()` restores it. An image URI newer than our own Copy (`ClipDescription.timestamp` vs `copiedAt`) is decoded (BitmapFactory, halved until ≤ 2400 px) and placed centred on the finger at its size in dp (≤ 60 % of the view, kept on screen); otherwise our own Copy is pasted, or a hint says how to copy an image. Tests: `aCutoutCanBeThrownOnTheWhiteboard`, `anImageCopiedInAndroidIsPastedOnTheWhiteboard`. Emulator note: after a reinstall grant POST_NOTIFICATIONS (`pm grant`, emulator only) or Android's prompt covers the tests; run them with `installDebug installDebugAndroidTest` + `am instrument` (connectedAndroidTest uninstalls the app).
- **Capturing the PC — solved with the panel's own Crop (2026-10-13, verified on the panel, v1.3.5):** Android can't read the HDMI/OPS picture, but ViewSonic's Crop (`com.seewo.cropscreen`, system uid, `/vendor/app/CropScreen`) can. Its service `com.seewo.cropscreen.services.CropScreenService` is exported without permission and is what the system bar starts (no extras). `PanelCrop`: on the PC source the scissors start it (`<queries>` lists the package); it saves a JPEG in `Notes/Mark/<date>/<time>.jpg` (media store, owner NULL), shows a "Saved" dialog (string `crop_save_success_title`, button `crop_save_success_close` "Terminar") and stays open until Exit (`id/crop_float_menu_close`, `crop_item_close` "Salida"); it broadcasts `com.seewo.intent.action.CROP_FINISH` when it closes (`CROP_START` on open). Marcar Pro polls the media store every 150 ms (READ_MEDIA_IMAGES, asked once through a card → `MainActivity` `ACTION_ASK_IMAGES`), decodes the new file at once, presses Terminar and Exit through the accessibility service (`TouchRelayService.press`, needs `flagRetrieveInteractiveWindows|flagReportViewIds`; labels read from the Crop's own resources) and places the cut-out on the whiteboard. Ahorrar → whiteboard ≈ 1.9 s (≈ 1.4 s is the panel's own capture). The file is then deleted, which needs "All files access" (MANAGE_EXTERNAL_STORAGE, the teacher turns it on once from a card; `createDeleteRequest` can't be shown from a service: "Missing calling package"). Without it the files stay. Only manifest/resources were inspected, never ViewSonic's code.
- **Selection menu on a moved whiteboard (fixed 1.3.3):** the menu is drawn and hit-tested in screen coordinates (it used to be laid out in board coordinates and ended up off screen after the board scrolled, e.g. after placing a cutout).

- **Lasso in the ring (1.3.9):** `RingToggle.LASSO` (icon `ic_lasso`, appended to existing ring orders) is a one-shot action, not a tool: it sets `AnnotationView.lassoNext`; the next pen or finger stroke (not an eraser) draws a lasso on any screen — on the whiteboard instead of panning — and selects what it surrounds, then everything is as before (a tap just cancels it). Holding a finger still and dragging still lassos too.
- **Accessibility prompt (2026-10-08):** when the scissors (every time) or a finger tap for the apps (once per session) need `TouchRelayService` and it is off, `PromptView` (a card in a layer window — an activity would open UNDER the ink overlay and get no touches) explains it; "Abrir ajustes" pauses the layer (Settings must be usable with the finger) and opens `ACCESSIBILITY_DETAILS_SETTINGS` for our service (refused for third-party apps on the emulator's Android 15 → falls back to the Accessibility list, where Marcar Pro is first). If the app-op `android:access_restricted_settings` is ERRORED (Android 13 sideload "restricted setting"), the text explains ⋮ › "Permitir ajustes restringidos" and the button opens App info instead. When the service connects (`TouchRelayService.onConnected`), the layer un-pauses and says so.
- **Latency findings on the panel (2026-10-09, measured with a temporary per-frame log + `dumpsys SurfaceFlinger --latency`; the probe was removed):** Android on the IFP7533 runs a single display mode, **3840×2160 at 30 Hz** (`mRefreshRateChangeable: false`), so touch→glass is ~100 ms (≈3 vsyncs) whatever the app does; ~25 ms of it is input→drawn. GPU: Mali-G52 **MC1**, DVFS 250→800 MHz over ~200 ms after the pen lands (`/sys/class/mpgpu/cur_freq`), hence 20–40 ms frames at the start of a stroke; the very first stroke after the process starts costs 150–285 ms (shader warm-up). Tried and rejected: (1) **CPU ink** (window without hardware acceleration, partial invalidation): ~150 ms touch→glass, worse, and the teacher felt it; (2) **own velocity predictor** (60 ms, then 30 ms with a turn/brake guard): visible "whiskers" on fast or abrupt moves, the teacher preferred yesterday's. Kept: androidx `MotionEventPredictor`, capped at `PREDICT_MAX_DP` 24 dp. The only real fix would be the vendor's writing service (hardware OSD plane), not open to apps by contract.
- **Messages (2026-10-09):** never Android `Toast`: on the panel they're suppressed when the app's notifications are off ("Suppressing toast … by user request"). `OverlayService.toast()` shows `HintView`, a dark pill in its own NOT_TOUCHABLE window at the bottom centre.
- **Ring (7):** Pen, Highlighter, Eraser, Hide ink, Magic ink (always neon pink with a glow, `Presets.MAGIC_COLOR`; fades after ~3 s), Shapes, Pupils (finger writes: several pupils at once; back of the hand erases).
  Tapping the active Pen/Highlighter/Eraser again opens its card palette (also from the orb's colour dot).
  A stroke keeps the tool it started with (`Live.tool`), even if the tool changes mid-stroke.
- **Trash** (separate, small, draggable): press-and-hold ~0.9 s clears everything (undoable).
- **Finger on ink:** 1st tap selects (dashed box, corner handles = scale, top handle = rotate; NO
  menu). Tap on the selected object toggles its menu (Copy, Duplicate, Colour, Delete). Dragging a
  selected object keeps it selected; dragging an unselected one just moves it. Two-finger pinch =
  scale + rotate. Release with speed → fling that bounces off the edges (deselects). With a
  selection, a tap on empty space only deselects (never reaches the app below). The menu is tied to
  the selection state (no selection ⇒ menu hidden) and never shows while a finger is down.
  Finger lasso on empty space = multi-select only if the finger cannot pass through to apps (plan B).
  Implemented in `AnnotationView` (region "Selection"): live gestures draw `lifted` strokes through
  `liveMatrix` and are applied on release (`Stroke.transform`, `History.Transformed`, undo = inverse);
  menu is drawn on the canvas (Copy, Duplicate, 6 colours → `History.Recolored`, Delete). Copy +
  long press on empty space pastes centred under the finger. Verified on the emulator: select, menu,
  colour, duplicate, rotate, corner scale, drag, fling + bounce, deselect tap, copy/paste, undo chain.
  Pinch verified with the instrumented test below.
- **Multi-touch:** ink and erasers are per pointer (`inking`/`erasing` maps in `AnnotationView`). In
  "finger writes" mode every finger writes and every fist erases at once; in the normal mode the first
  writer wins (palm rejection), and fingers never interrupt ink. Erasing by several erasers at once is one
  undo step. Simultaneous fist erasers are untested (the emulator can't fake the IR contact size).

- **Whiteboard (2026-10-05):** a separate draggable button (`MiniOrbView`, 64 dp window, first at the bottom right like the old mode orb, position saved as "whiteboard"; `AREA_WHITEBOARD`). One finger on empty paper that moves → pan; a second finger → zoom (0.2–5×) about the fingers; while the camera moves, ink is drawn as vectors (culled to the visible area) and the layer is re-rasterised after.
